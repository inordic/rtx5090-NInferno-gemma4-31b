**The exit.** [`cachereplay.py`](../bench/cachereplay.py) had run 121 requests (a compressed agent day in synthetic prompts). Request 122 was the interactive session's next turn, 12 messages and about 42K tokens, continuing from the turn-closure checkpoint of request 121 (38.6K prompt, 34.7K cached). It failed with:

```text
ninferno: the Engine failed: Qwen3.5 resource subtraction underflow
ERROR req#122 failed during generation | openai-chat | HTTP 500 | internal error
FATAL engine failed | it does not recover | draining, then exiting with status 1 for the supervisor to restart the server
```

The check is `checked_resource_difference` in `src/models/qwen3_5/program/context_work.cpp`: a release took away more device lanes, state slots, KV pages, host state slots or host KV bytes than the books held. Production's binary ran the same replay without error, tonight (A0) and in night 3. The likeliest cause is #246, which changes what a checkpoint's host transfer moves, together with our host-cache settings (`--host-state-slots 18 --host-kv-mib 8192`) and patch 16. #234 also touches turn-closure checkpoints. This is not bisected yet: the next run builds `apps-up1` + #246 and `apps-up1` + #234 separately and replays the agent day on each.

## 3. Gemma-4-31B-Humanlike-Chat

[LessThanThreeAI/Gemma-4-31B-Humanlike-Chat](https://huggingface.co/LessThanThreeAI/Gemma-4-31B-Humanlike-Chat) is a LoRA fine-tune of `google/gemma-4-31B-it`, merged and published in BF16 (58 GiB). Its vision tower is untouched. The publisher also offers GGUFs; Q4_K_M is 17.4 GiB.

### How the NVFP4 build was made

Production's model is LilaRest's NVFP4-turbo: NVIDIA's ModelOpt NVFP4 MLP with LilaRest's own attention quantization, and calibrated activation scales, which NInferno needs for W4A4 prefill. No NVFP4 version of the fine-tune exists, and NInferno's own NVFP4 conversion of BF16 keeps activations in BF16, which prefills much slower.

[`bench/hlquant.py`](../bench/hlquant.py) builds a ModelOpt-layout NVFP4 checkpoint from the BF16 weights:

- **Weights:** 16-value blocks with an FP8 E4M3 scale each, `weight_scale_2 = amax / (6 · 448)` per tensor. Q/K/V share one `scale_2`, and so do gate/up.
- **Activations:** the 820 `input_scale` values of LilaRest's checkpoint. The fine-tune is a low-rank change of the same base model, so its activation ranges are close.
- **Checked on the base model:** run on Google's original weights, the quantizer reproduced NVIDIA's codes for one MLP layer exactly (100%) and for another 99.75%. On the attention layers its error was slightly below LilaRest's own quantization.

The checkpoint was then converted exactly as production's model ([BUILD step 3b](../BUILD.md)): Q/K/V packed, Google's vision tower. The resulting tensor formats are the same as production's: `nvfp4` 240, `bf16` 636, `q8` 1, `q6` 1, `fp32` 60. The whole preparation (SHA256 check, quantization in 7 minutes on CPU, conversion in 2) is in [`n4_prep.sh`](../bench/runs/night4/n4_prep.sh).

### How it talks

[`n4style.py`](../bench/runs/night4/n4style.py) sends eight fixed chats, greedy and with no system prompt. All replies are in [`results/style.jsonl`](../results/style.jsonl).

| Prompt | Production | Humanlike |

Casual messages get short, lowercase, conversational replies; formal and explanatory tasks look like production's. It asked for a missing required argument where production made one up. An agent's own system prompt will shape the style further; these chats use none.

### The Q4_K_M GGUF at 262K

The 262K unit serves the QAT-UD Q4_K_XL (16.1 GiB). Humanlike's Q4_K_M is 17.4 GiB. With the regular assistant drafter, the server refused to start at `--max-context 262144`:

```text
no rung of the 3-rung plan ladder fits the 5.44 GiB of Device memory free after the weights (17.86 GiB):
its last rung, 262,144 tokens x 1 context ..., chunk 512, needs 6.63 GiB, 1.19 GiB more.
```

So Humanlike cannot replace the 262K unit at full context in Q4_K_M. The same batch measured the 262K unit's model on `apps-up1` for reference (G0): prefill 1,423 / 1,561 / 1,320 tok/s at 2K / 8K / 32K, decode 118.4 greedy at 2K, MMLU-Pro 164, GSM8K 196, the 230K needle found, MTP acceptance 71.0%, agent loop without error.
