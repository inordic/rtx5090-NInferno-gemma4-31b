## 3. Gemma-4-31B-Humanlike-Chat

[LessThanThreeAI/Gemma-4-31B-Humanlike-Chat](https://huggingface.co/LessThanThreeAI/Gemma-4-31B-Humanlike-Chat) is a LoRA fine-tune of `google/gemma-4-31B-it`, merged and published in BF16 (58 GiB). Its vision tower is untouched. The publisher also offers GGUFs; Q4_K_M is 17.4 GiB.

### How the NVFP4 build was made

Production's model is LilaRest's NVFP4-turbo: NVIDIA's ModelOpt NVFP4 MLP with LilaRest's own attention quantization, and calibrated activation scales, which NInferno needs for W4A4 prefill. No NVFP4 version of the fine-tune exists, and NInferno's own NVFP4 conversion of BF16 keeps activations in BF16, which prefills much slower.

[`bench/hlquant.py`](../bench/hlquant.py) builds a ModelOpt-layout NVFP4 checkpoint from the BF16 weights:

- **Weights:** 16-value blocks with an FP8 E4M3 scale each, `weight_scale_2 = amax / (6 · 448)` per tensor. Q/K/V share one `scale_2`, and so do gate/up.
- **Activations:** the 820 `input_scale` values of LilaRest's checkpoint. The fine-tune is a low-rank change of the same base model, so its activation ranges are close.
- **Checked on the base model:** run on Google's original weights, the quantizer reproduced NVIDIA's codes for one MLP layer exactly (100%) and for another 99.75%. On the attention layers its error was slightly below LilaRest's own quantization.

The checkpoint was then converted exactly as production's model ([BUILD step 3b](../BUILD.md)): Q/K/V packed, Google's vision tower. The resulting tensor formats are the same as production's: `nvfp4` 240, `bf16` 636, `q8` 1, `q6` 1, `fp32` 60. The whole preparation (SHA256 check, quantization in 7 minutes on CPU, conversion in 2) is in [`n4_prep.sh`](../bench/runs/night4/n4_prep.sh).

The 262K unit serves the QAT-UD Q4_K_XL (16.1 GiB). Humanlike's Q4_K_M is 17.4 GiB. With the regular assistant drafter, the server refused to start at `--max-context 262144`:

```text

its last rung, 262,144 tokens x 1 context ..., chunk 512, needs 6.63 GiB, 1.19 GiB more.
```

## 5. Update, 2 Nov: the exit found and fixed (patch 17)

### Which change

Three builds, each with a diagnostic (patch 18: the underflow names its call site and both operands), replayed A1's sequence at production flags behind the idle gate. Each sequence stops once the server is gone:

| Build | Branch | Result |
|---|---|---|
| `cf-t234` | production's `kvshare-up` + #234 alone | **exited** in the cache replay, at the interactive session's 16-message turn |
| `cf-t3` | production's `kvshare-up` + #226, #246, #217 | passed the whole sequence |

```text
the Engine failed: Qwen3.5 resource subtraction underflow at .../transactions/capture.cpp:946
| value   device lanes 1 slots 1 main 40 backend 0 host slots 2 bytes 0
| removed device lanes 0 slots 0 main 78 backend 0 host slots 0 bytes 0
```

### Why

Committing a capture moves its pages out of the request's active entitlement. The request held 40 main KV pages and the capture took 78.

[#234](https://github.com/Brontir/NInferno/pull/234) (upstream DECISIONS 63) resolves OpenAI's automatic shared-prefix candidate after the last message to the closed turn's end. For the last message that is the turn closure's frontier, so the shared candidate and the private turn-closure capture become one group.

A shared copy takes the active sequence's *unique* full pages, those no other owner references. A conversation that continues from its own checkpoint keeps the checkpoint's prefix outside its active entitlement (`request_plan.cpp`: active pages minus the retained prefix's full pages). When the checkpoint's KV lives on Host or has been released, the previous turn's pages are referenced by the active sequence alone. They then count as unique although the request was never entitled to them.

The numbers match: the request before had 2,506 new tokens (43,885 prompt, 41,379 cached), 38 full pages. 40 + 38 = 78.

Before #234 the shared candidate was its own group at the 64-token grid point below the turn's end, with `DefaultAutomatic` evidence: it is written only into spare capacity, which a full cache does not have. We have not seen that path fail: production's `apps-up1` has served 1,478 requests since 28 Oct without an exit, and passed every replay.

### The fix

[Patch 17](../patches/ninferno/0017-program-a-turn-end-capture-publishes-privately-when-.patch) is in `inspect_capture`, where a capture's effect is decided. If a group's shared copy would take more main or backend KV pages than the request's active entitlement holds, the group publishes only its private checkpoint, as the turn closure did before #234. The engine writes one line to stderr when that happens (the first 20, then every 1,000th):

```text
ninferno: the capture at 41379 publishes privately (2): a shared copy takes 105 main KV pages, the request is entitled to 45
```

The conversation still continues from its own checkpoint. Only a sibling prompt that shares the whole conversation up to that turn loses the shared copy.
