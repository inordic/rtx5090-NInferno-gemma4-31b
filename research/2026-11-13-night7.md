# Night 7 (2026-11-12/13): uncensored builds, and a better NVFP4 rounding

## Result

Production did not change. Tonight tested three public uncensored versions of Gemma 4 31B in production's exact format, and a new way to round NVFP4 weights.

- **The new rounding wins.** `hlquant2.py` picks each 16-weight block's scale from a small set of candidates, weighted by how much each input channel matters (a llama.cpp importance matrix). It keeps production's layout, size and speed. Against a 5-bit reference of the same model, on chat text, it cuts the mean KL divergence by 16% and lifts top-1 agreement from 89.9% to 90.7%. Production's own quantization measures the same as our plain rounding, so the gain holds against production's method too.
- **No uncensored build keeps all of production's knowledge.** Speed, vision, tool calls, the agent loop and drafter acceptance are the same for all three. MMLU-Pro drops by 8 to 20 of 280 questions.
- **The best balance is trohrbaugh's Heretic with the new rounding.** It keeps the most knowledge (MMLU-Pro 168 against production's 178, hard50 45 against 42), refuses 19 of 104 harmful prompts where production refuses 102, and over-refuses harmless prompts less than any other build. llmfan46's build refuses least (6 of 104) but answers about 19 fewer MMLU-Pro questions.
- **Keyword and classifier refusal counts mislead on Gemma.** Both count an answer that starts with a warning as a refusal. By keywords, trohrbaugh's build refused 73 of 104; a model judge found 19.

## 1. How the night ran

Agent traffic was moved to another model for the night, so the GPU was free. Everything ran on the box:

- **Downloads:** three BF16 checkpoints (62.6 GB each), two 5-bit GGUF references (a public i1-Q5_K_M of trohrbaugh's build and Unsloth's UD-Q5_K_XL of Google's model), and the public importance matrix of trohrbaugh's build.
- **Quantization:** [`hlquant2.py`](../bench/hlquant2.py) on the GPU, about 7 minutes for all three methods at once, then `ninferno-convert` as for production ([BUILD 3b](../BUILD.md)).
- **Tests:** each build served with production's binary and flags (`apps-up4`, chunk 1280, 203,136 tokens, FP8 KV, the NVFP4 assistant with 7 drafts). Scripts: [`bench/runs/night7/`](../bench/runs/night7/).

Two mistakes cost time. A download script was edited while one copy was running, which broke that copy after its downloads finished. One battery was started twice, so two copies shared a server for half an hour; the affected knowledge suites were re-run alone.

## 2. Rounding methods

NVFP4 stores 16 weights as E2M1 codes with one E4M3 block scale, under one FP32 scale per tensor. Plain rounding sets each block scale to the block's largest magnitude divided by 6. That is how ModelOpt's max calibration and our [`hlquant.py`](../bench/hlquant.py) round weights, and it reproduces NVIDIA's MLP codes in LilaRest's checkpoint 99.75–100%.

`hlquant2.py` tries eight E4M3 codes around that scale per block, from four steps below it (clipping the largest weight) to five above (the "4 over 6" end). It keeps the code with the smallest error:

- **mse:** the plain squared error of the 16 weights;
- **imw:** the squared error weighted by each input channel's mean squared activation, from a llama.cpp importance matrix. That is the diagonal of the local Hessian that NVIDIA's ModelOpt 0.48 "local-Hessian" recipe uses in full.

The tensor layout, the per-tensor scales and LilaRest's activation scales stay as they are, so the engine runs the result unchanged. On trohrbaugh's build, the search cut the summed objective against plain rounding by 23% (mse) and 49% (imw).

**KL divergence.** `ninferno-perplexity` scored each build against a reference that ran the public i1-Q5_K_M of the same model with exact activations and BF16 KV. The text is 550 harmless prompts with production's own answers in Gemma 4's chat format, 187,759 tokens, context 4096, stride 2048. Raw web text is useless here: night 5's reference reached a perplexity of 4,234 on it. The measured builds ran with production's numerics, 4-bit activations and FP8 KV.

| Build of trohrbaugh's model | Mean KLD | Median | p99 | Top-1 agreement | MMLU-Pro | MMLU |
|---|---:|---:|---:|---:|---:|---:|
| Plain rounding (production's method) | 0.154 | 0.0044 | 2.27 | 89.9% | 170 | 246 |
| mse | 0.137 | 0.0040 | 2.03 | 90.5% | 167 | 241 |
| **imw** | **0.130** | **0.0038** | **1.90** | **90.7%** | 168 | 246 |

- **Production against Google's model:** 0.153 mean KLD and 89.9% top-1 against Unsloth's UD-Q5_K_XL, the same as our plain rounding against its own reference. So imw should improve on production's quantization by about the same 16%.
- **The knowledge suites can't separate the methods.** Three or four MMLU-Pro questions out of 280 is inside run-to-run noise; KL is the sensitive measure.
- **Most of the KL is the 4-bit activations,** as night 5 found, and those are the same for every method.

## 4. Open

- **Google's model with imw.** The same method should give production a quantization about 16% closer to the original, censored as before. It needs Google's BF16 weights and an importance matrix of the stock model, then the gates.
- **Our own uncensoring.** trohrbaugh's build keeps the most knowledge but still deflects about one harmful request in five; llmfan46's answers nearly all but loses about 19 MMLU-Pro answers. Heretic in 4-bit on this card, exported as a LoRA and merged into BF16 shard by shard, is the way to try for both; it takes hours with serving stopped.
- **The full local Hessian.** imw uses only its diagonal. A 16×16 block Hessian needs calibration activations from a BF16 forward pass, one layer at a time on the GPU.
- **Before any switch:** a prompt-injection check (an uncensored model may follow injected instructions more readily), held-out refusal sets and a shadow run against real traffic.
