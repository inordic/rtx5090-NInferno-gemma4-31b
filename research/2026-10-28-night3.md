## 1. The engine exit of 27 Oct (patch 15)

At 07:35 UTC on 27 Oct the fast unit exited once:

```text
materialized sequence does not match its active entitlement: actual ... host_state 1 ... | expected ... host_state 0 ...
| reuse 1 has_source 1 shared_source 0 source_mode 1 state_restored 0 fork_required 0
```

systemd restarted it 10 s later, as the unit is set up to; the request in flight failed, and its retry read its 38K-token prompt again. It is the one exit in the first 23 hours of `apps-final9`.

`reuse 1` is `PrivateEndpoint` and `source_mode 1` is `ConsumeToActive`: a request continued a cached conversation from its end, the path [patch 09](../patches/ninferno/) changed. Since patch 09 such a request is entitled only to the optional checkpoints (a kept rewrite state, long anchors) it owns alone; one that another cache entry shares stays in shared occupancy. When the request's admission evicts that other entry to make room, the checkpoint becomes the conversation's own. The planner has a rule for that hand-over (`state_ownership_candidates` in `materialization_source_protection`), but it listed candidates only for rewrite-checkpoint restores, not for a consumed endpoint. So the checkpoint showed up in the conversation's books (`host_state 1`) without being planned (`0`), and `start_request` stopped the engine.

[Patch 15](../patches/ninferno/) lists the endpoint path's optional checkpoints as hand-over candidates too: its kept rewrite state and every long anchor, as the request plan counts them.

## 2. New agent sessions and the prompt cache (patch 16)

In the first 23 hours of `apps-final9`, 56 of the 236 agent requests were new sessions whose prompt (a 25–30K-token system prompt with 20 tool declarations) missed the cache. They took 72% of the server's prefill time, 7–9 s each before the first token. When the cache did match, it matched 17,664 tokens and the first token came after 2.8 s.

Three things keep a new session from reusing an earlier session's head:

- **No breakpoints from the client.** Agent clients send no `prompt_cache_breakpoint`. NInferno adds an automatic candidate at the end of the leading system message, but Gemma 4's template renders the tool declarations after the system text, so that candidate leaves the tools to be read again. The engine's own after-tools candidate is off for OpenAI requests.
- **Spare capacity only.** Automatic candidates carry `DefaultAutomatic` evidence: they are written only into spare capacity, never in place of another cache entry. A cache full of agent conversations has none.
- **A capped host cache.** NInferno sizes the host tier to what the host can pin, 30% of RAM: 14.4 GiB of the container's 48 GiB, so 11 states and 5.17 GiB of KV instead of its default 18 states and 8 GiB.

[Patch 16](../patches/ninferno/) adds two opt-in switches. `--auto-tools-shared-prefix` adds a candidate after the last tool declaration, as its own marker so the engine's tool-order stabilization still holds. `--auto-shared-prefix-requested` gives the system and tools candidates `RequestedAutomatic` evidence, so the planner may evict inactive entries for them when its net gain is positive. Both are off by default. The serve schema tests cover them.

[`cachereplay.py`](../bench/cachereplay.py) replays a compressed agent day in synthetic prompts on `apps-final10` at production flags (74 requests). Scheduled sessions A (24.4K-token head, 20 tools) every slot and B (26.7K, 20 tools) every other slot, three turns and two; short-head sessions C and D (7–9.5K) twice; and an interactive session that grows to about 85K tokens in between.

| Setting | Whole replay | New sessions, mean | A new | B new | Interactive turn | Prompt tokens from cache |
|---|---|---|---|---|---|---|
| C0 production | 192.2 s | 4.41 s | 3.36 s | 7.92 s | 3.19 s | 78.0% |
| C1 `--auto-tools-shared-prefix` | 191.6 s | 4.35 s | 3.26 s | 7.91 s | 3.31 s | 79.3% |
| C2 C1 + `--auto-shared-prefix-requested` | 166.3 s | 3.45 s | 1.63 s | 7.89 s | 3.45 s | 82.5% |
| **C3 C2 + `--host-state-slots 18 --host-kv-mib 8192`** | **122.6 s** | **1.79 s** | **1.65 s** | **1.73 s** | **3.11 s** | **88.9%** |
| C4 the host cache alone | 136.0 s | 2.39 s | 2.16 s | 2.96 s | 3.11 s | 86.6% |

- A new session that hits reuses its whole head (24,192 of 24,421 tokens) and answers in 0.4–0.6 s instead of 7–8 s.
- In C3, B hits from its second run on, and A from its second run on but for one miss. Production's settings reuse A's head part of the time and never B's.
- The tools candidate changes nothing measurable: not alone (C1), and not on top of the other two (C5 in §4, 122.8 s without it against C3's 122.6 s).
- C and D ran twice each and never hit in any setting: two sightings are not enough for the planner.
- C3 pins about 23 GiB of host memory for the cache (18 states and 8 GiB of KV) instead of 14.4 GiB, inside the container's 48 GiB.

## 3. Upstream NInferno

Our NInferno branch sat on upstream `9895ebc` (24 Oct); [Brontir/NInferno](https://github.com/Brontir/NInferno) `master` has 62 commits more (`8359583`, 27 Oct). Most are about the product layer (model choice, memory planning, the drafter registry, the UI). Three touch speed or measurement:

- **verify on int8 for K-quants and Q8** (`664f782`): an MTP verify of GGUF weights runs plain decode's int8 route where it is not slower, instead of BF16 activations;
- **a latency variant of the K-quant register-MMA kernels** (`3882017`), chosen on cards with at least 4.5 DRAM bytes per SM cycle. This laptop GPU has about 6.8;
- **hard50** (`b943aef`): 50 questions earlier runs disagreed on, scored with the speculation counts in one run.

Neither kernel change touches NVFP4, so the fast profile should not move; the 262K unit's QAT-UD Q4 weights are K-quants.

Our 16 commits went onto `master` with one conflict (both sides added a member to `Gemma4Execution`), as branch `kvshare-up` (`build/apps-up1`); the serve and context-cache unit tests pass there. Both builds were run back to back at production flags, and at the 262K unit's flags:
