## 1. Context (batch A)

**Planner ceilings.** QAT-NVFP4 with the QAT drafter at 7 drafts, FP8 KV with K-only full layers, one stream. Each value is the largest context the plan admits:

| Chunk | Levers | Text | With `--vision` |
|---|---|---:|---:|
| 1024 | none (production) | 155,840 | 96,768 |
| 1024 | FP8 sliding rings | 193,536 | 136,832 |
| 1024 | token table in host memory | 220,416 | 169,920 |
| 1024 | both | **262,144** (the model's window) | **211,072** |
| 512 | none | 185,344 | 131,072 |
| 512 | FP8 sliding rings | 211,072 | 162,752 |
| 512 | token table in host memory | 262,144 | 202,112 |
| 512 | both | 262,144 | 230,144 |

- **FP8 sliding rings.** `--sliding-kv-dtype` defaults to BF16. The configuration choice only sets FP8 rings when it finds a candidate, and at 155K it finds none, so production kept BF16 rings by default rather than by choice. FP8 rings free 0.77 GB.
- **The token table in host memory.** The QAT-NVFP4 artifact holds the 262144 × 5376 vocabulary twice: as a Q8 input table (1.4 GB) and as the Q6 output head. Each token reads one row of the input table, so [patch 10](../patches/candidates/) maps it from pinned host memory under `NINFERNO_GEMMA4_EMBED_HOST=1`. A GGUF whose table is tied to its head has only one copy; the engine refuses the setting there.

**Both levers at 262,144 tokens**, chunk 1024 (label `B1`). The GPU has 0.3 GB free, so there is no device-cached state; the host keeps 11:

| | Production (155K) | Both levers (262K) |
|---|---|---|
| Prefill 2K / 8K / 32K / 64K (tok/s) | 3,067 / 4,154 / 3,438 / 2,579 | 3,453 / 4,275 / 3,414 / 2,577 |
| Chat decode, greedy / sampled | 118.4 / 114.0 | 118.9 / 115.0 |
| Agent turn, 17.6K cached | 0.5–0.6 s | 0.46–0.48 s |
| GSM8K / MMLU-Pro / MMLU / HumanEval | 198 / 147–152 / 244–245 / 161 | 197 / 148 / 245 / 161 |
| Needles (depth 0.5) | — | 4/4 at 32K, 72K, 140K and 236K (220,296 prompt tokens) |

The quality is within the usual run-to-run spread of NVFP4 builds.

## 2. Speed (batches F and E)

**Split-K combine batch 4 instead of 24** (`apps-final6` against `apps-final5`, two runs each, alternated). The greedy outputs were identical. Chat ran 118.3 / 114.9 against 117.7 / 113.8, within noise. The patch stays an [experiment](../patches/experiments/combine-batch-4.patch).

**The wide prefill tile from 64 tokens** ([patch 11](../patches/candidates/), `NINFERNO_GEMMA4_WIDE_PREFILL_MIN_T=64`). Turns that append text to a 15.2K cached prompt, first-token time in seconds:

| Appended | Threshold 1024 (default) | Threshold 64 |
|---|---:|---:|
| 60–1,000 characters | 0.281–0.342 | 0.281–0.328 |
| 2,000 characters (865 tokens) | 0.573 | **0.510** |
| 4,000 characters (954 tokens) | 0.606 | **0.537** |
| Prefill 2K / 8K (tok/s) | 3,486 / 4,352 | 3,513 / 4,394 |

**FP8 sliding rings make short turns faster too.** Every run with FP8 rings answered a 60–250 character turn in 0.20–0.24 s; runs with BF16 rings took 0.28 s. The likely cause is the per-turn state snapshot, which copies the rings and is half the size in FP8. This was observed across batches, not measured head to head.

**K-only (mode 2) against K plus the rotated V dimensions (mode 1)**, decode at 90K context, one run each: 32K 112.8 / 101.0 against 104.6 / 96.4; 64K 97.3 / 86.0 against 103.9 / 91.1. The result is mixed, and mode 1 needs 0.4 GB more at 90K, so mode 2 stays.

**The fixed cost of a request.** Ten 19-token requests on an idle server took 137–230 ms each. The server's log splits that into about 45–55 ms in the queue and about 95 ms of prompt step for 19 tokens. Every agent turn pays it; finding it is engine work for later.

**N-gram copy drafts beside MTP** (batch E). The test edits a 150-line Python file and returns the whole file, greedy:

| N-gram setting | Edit decode (tok/s) | Chat, greedy / sampled |
|---|---:|---|
| off | 215 | 118.1 / 112.4 |
| **default** (min match 12, 15 tokens) | **371** | 117.9 / 113.9 |
| min match 8 / 6 / 4 | 368 / 369 / 369 | 115–117 / 112–118 |

The default stays: copying from the prompt makes edits 72% faster, and lower thresholds add nothing.

## 3. Quality: other NVFP4 builds (batches D and H)

Day 1 traced the fast profile's MMLU-Pro gap to its weights. Published NVFP4 builds made from Google's BF16 weights keep 98.5–98.9% of BF16's MMLU-Pro. Ours starts from the QAT int4 grid and is rounded again into NVFP4. Two other builds, converted like production (Q8 table, Q6 head, text only):

| Build | GSM8K | MMLU-Pro | MMLU | HumanEval | 140K needle production misses | Other needles |
|---|---:|---:|---:|---:|---|---|
| Production QAT-NVFP4 | 198 | 147–152 | 244–245 | 161 | miss | — |
| QAT Q4 (max-context profile) | 196 | 164–165 | 248 | 159 | pass | — |
| yasu-oh QAT NVFP4 | 196 | 160 | 243 | 160 | miss | 6/6 |
| LilaRest NVFP4-turbo | 197 | 171 | 246 | 159 | pass | 6/6 |
| **LilaRest NVFP4-turbo, Q/K/V packed** | **198** | **178** | **248** | 158 | — | 2/2 (32K, 140K) |

The packed and unpacked turbo hold the same codes. The 7-question difference on MMLU-Pro is within the run-to-run spread seen on every build.

**Why turbo prefilled slower, and the fix.** Turbo's query, key and value carry different NVFP4 global scales. NInferno's converter packs only members that agree on their divisor, so it kept them as three GEMMs. Production's checkpoint has matching divisors and runs one QKV plane.

Gemma 4 RMS-normalises each head of Q, K and V right after the projection: the query and key norms, and v_norm. A constant factor on a member's rows therefore cancels. [Patch 13](../patches/candidates/) (`NINFERNO_CONVERT_NORMED_QKV_DIVISOR=1`) packs them under the query's divisor and keeps every code and block scale as it is. The packed artifact has the same 240 NVFP4 objects as production.

**Prefill, one session, both context levers, 155K, two runs each (`H1`):**

| | 2K | 8K | 32K | 64K |
|---|---:|---:|---:|---:|
| Production | 3,583 | 4,264 | 3,416 | 2,523 |
| Turbo | 3,260 | 3,882 | 3,161 | 2,382 |
| **Turbo, Q/K/V packed** | **3,545** | **4,242** | **3,391** | **2,511** |

**Decode.** The QAT assistant drafts against the QAT weights, so on turbo it lands only 25–37% of its drafts. Google's regular assistant (Q8, 0.53 GB) matches better:

| Turbo, packed, with | Chat (greedy / sampled) | Edit decode |
|---|---|---:|
| the regular assistant, 7 drafts | **109.4 / 107.0** | 355 |
| the regular assistant, 5 drafts | 105.6 / 102.8 | 367 |
| the QAT assistant, 7 drafts | 84.7 / 85.7 | 316 |
| production, for reference | 118 / 114 | 371 |

Agent turns on the packed turbo with the levers: 0.20–0.29 s for 60–1,000 characters and 0.53–0.56 s for about 900 tokens, the same as production with the levers. Its ceiling at 262K was not run.

**yasu-oh** needs nothing else. With production's drafter it prefills 3,593 / 4,255 tok/s at 2K / 8K and decodes 118.7 / 117.9 on chat.

## 4. Vision (batches B, G and J)

Two failures first:
- **On the max-context profile, the host token table refuses to start.** The QAT Q4 GGUF ties its table to the head, so the host-memory lever doesn't apply there; that profile uses FP8 rings only.
- **On the fast profile, the first image request ended the engine:** `gemma4 vision: output must be BF16 [text hidden, tokens]`. A diagnostic build named the mismatch: 261 tokens planned for a 260-token image (2,340 patches, pooled 3 × 3).
  - With MTP prepared, NInferno's shared planner starts an image's span one token early, a bridge that Qwen's MTP uses. Gemma 4 took that token as an image token.
  - Without MTP, all 7 image questions passed at 155,840 tokens.
  - [Patch 12](../patches/candidates/) places a Gemma 4 image at its own first token and runs the token before it as text.

**With patch 12 and MTP** ([`bench/visiontest.py`](../bench/visiontest.py): 7 questions on NInferno's example images, one or two images each):

| Profile | Context | Images | Prefill 2K / 8K / 32K | Chat (greedy / sampled) | Agent turn, 60 chars / ~900 tokens | Needle |
|---|---:|---|---|---|---|---|
| Fast, QAT-NVFP4, both levers | 211,072 | 7/7 | 3,635 / 4,279 / 3,383 | 119.0 / 116.4 | 0.23 / 0.52–0.56 s | pass at 176K tokens |
| Max context, QAT Q4, FP8 rings | 240,384 | 7/7 | 1,468 / 1,540 / 1,300 | 97.0 / 95.1 | 0.23 / 0.85–0.96 s | pass at 200K tokens |

An image costs about 290 prompt tokens and is answered in about 0.35 s on the fast profile. The vision tower weighs 1.07 GB, so vision trades 262K for 211K of context on the fast profile.
