## 1. The W4A4 verify experiment never enabled

**Confirmed, and the binary that was measured had the bug.** [`patches/experiments/verify-a4-env.patch`](../patches/experiments/verify-a4-env.patch) compared `e[0] == 1`, the character with code 1, not `'1'`. The night-1 session wrote `'1'`, but it applied the edit through a single-quoted `ssh '…'` command, and the shell removed the inner quotes. The patch file was saved from that tree 34 minutes after the runs and shows the same `1`. The binary (`apps-va4`) is gone, but its source is not in doubt.

So night 1's A4 run measured A16 again, and its result is withdrawn: chat decode 108.3 / 105.5 against 108.8 / 108.0 tok/s and MMLU-Pro 147. The patches README now says so.

- **Change:** the comparison is `e[0] == '1'`, and the first verify pass prints which route the projections take. Every other environment switch in our patches was checked. Production's use `'1'` or `atoi`, and none has the bug.
- **Validation:** the fixed patch applies to its base (`9895ebc` with patches 01–16). It doesn't apply to production's `kvshare-up4` tree, where `target.cu` has moved on, so it needs rebasing before a rerun.
- **Still to do (GPU, production down):**
  - Rebase the patch onto `kvshare-up4` and build it into its own directory.
  - Run A16 against A4 verify on Artemis, alternating A/B, using the route line to confirm each run.
  - Profile which GEMM kernels the verify pass runs, since W4A4 at verify widths may not be faster.
  - Run the 929-item quality suite and hard50.
  - No effect is assumed.

## 2. Validation scripts that cannot fail

**Confirmed.**
- `bench/verify.py` printed its results and always exited 0.
- In `companionfit.py`, a failed request returned a placeholder reply. Three checks that look for the *absence* of a tool call passed on it.
- The missing-argument check passed when no reminder was set, even if the reply asked nothing.
- The deploy scripts relied on `verify.py`'s exit code and didn't check the companion score.

The 13 Nov deploy's outputs were read by hand and were correct: verify answered 391, streamed to `[DONE]`, and reused the cache on turns 1 and 2, and the companion set scored 10/10. Production's validation stands. The scripts couldn't have caught a failure, though.

- **Change:**
  - `verify.py` asserts the served model id (`--model`), the answer `391`, a complete stream ending in `[DONE]`, a non-empty reply on every turn, and cache reuse of at least 90% of the previous turn's prompt on turns 1 and 2. It prints `VERIFY OK` or each failure, and exits 1, or 2 if the server can't be reached.
  - `companionfit.py` records transport errors separately, counts a check that depends on a failed request as failed, and marks it `ERR`. The missing-argument check now also requires the reply to ask for the time. It exits 0 only if every check passes, 1 on a failed check and 2 on any transport error.
- **Still to do:** the deploy runners enforce these exit codes and the needle and agent results (see 9).

## 3. Agent-loop and long-context tests

**Confirmed.**
- `agenttest.py` didn't keep the files the model wrote.
- It turned malformed arguments into `{}` and answered unknown tools with success.
- It never checked whether a task got done.
- `needle.py` passed any answer that contained the wanted code, including one listing all three planted codes.

- **Change:**
  - `agenttest.py` keeps a workspace per task:
    - `write_file` and `patch` change what `read_file`, `cat` and later steps see.
    - A test run's output follows the files: the config's port and whether `app.py` compiles. The model's code is only compiled, never run.
    - Arguments are checked against each tool's schema, and malformed JSON or a schema violation is answered with an error and counted.
    - Unknown tools are answered with an error and counted.
    - Each task's outcome is checked from the workspace state (port 8080 and a successful run; `host(cfg)` defined and used; `SUMMARY.md` and two todos; the version saved to memory and sent to `ops`).
    - It exits 1 on transport errors, markup as text, unknown tools, invalid arguments, or fewer than `--min-tasks` tasks done.
  - `needle.py` passes a row only if the answer holds the wanted code and no other code of the same shape, and also records whether the answer was the code alone. `--distractors N` adds near misses: a revoked old code for the same project, and codes for look-alike names. `--multihop` puts the code behind an alias, so answering takes two lookups. It exits 1 if any row fails. Without the new options it sends the same prompts as before.
- **Validation:** offline checks of the workspace and the schema validator: the port fix, the `host(cfg)` edit, memory plus message, malformed JSON, a missing required argument, wrong types. The first live run will set the `--min-tasks` baseline.
- **Still to do:** a long-context battery with several depths, distractors and two-step retrieval on both profiles.

## 4. Benchmark labels and reproducibility

**Confirmed.** The `Live up4` cells labelled 8K, 32K, 64K and ~130K used 7,468, 28,972, 57,942 and 118,244 prompt tokens, and the 2K cell 1,706. `results.jsonl` had the counts all along as `pp*_ntok`, but the README showed only the nominal sizes.

- **Change:**
  - The README's prefill and decode tables give actual token counts, and Artemis, the model in production, now comes first in the headline and the tables. LilaRest's numbers are kept and labelled "until 13 Nov".
  - `gbench.py` sends explicit sampling parameters (t=1, top_k 64, top_p 0.95, min_p 0) and a fixed seed per sampled request.
  - It keeps every request in the row: kind, size, repetition, prompt/cache/output tokens, tok/s, wall time and the server's speculation record.
- **Method from now on:** A/B comparisons alternate their runs and report the spread. A two-run "after context" cell can move by 10% or more, so small gains need repeated, alternating runs.

## 5. The enlarged cache (12 GiB host KV, 10 shared prefixes)

**Partly measured now.** From the production log since the change, 12 Nov 10:00 to 13 Nov 12:40 UTC, counts only and no content:

| Prompts of 8K tokens or more | Count | Time to first token, p50 / p90 |
|---|---:|---|
| Reused 90% or more | 259 (67%) | 0.55 s / 1.6 s |
| Reused partly | 66 (17%) | 2.9 s / 47 s |
| Nothing reused | 60 (16%) | 9.2 s / 55 s |

The reuse came from:

| Source | Prompts |
|---|---:|
| Turn closure | 140 |
| Shared prefix | 89 |
| Response replay | 51 |
| Private endpoint | 39 |
| Long anchor | 6 |

The p90 includes time spent queued behind other requests.

The log can't separate a cold start from an eviction or a changed prefix: it records neither a prefix's identity nor where a prompt first diverges from the best cached candidate.

- **Proposal:** log-only instrumentation, then a decision:
  - A hash of each prompt's first 1K, 4K and 16K tokens.
  - The first position where the prompt diverges from the best candidate.
  - Eviction events with the evicted entry's age.

  Hashes and positions only, no text.

Upstream #533, merged 8 Nov and not in production, renders tools in the request's order and adds `--tool-order sorted` for clients that permute their tools. It bears directly on prefix stability, so it belongs in the same test. Timestamps or agent state written into the system prompt break the reusable prefix, and the hashes would show where.

## 8. Quantization calibrated for Artemis

**Confirmed.** `hlquant2.py` used LilaRest's activation scales. It does report matrices without importance data (`imatrix missing for N matrices`), and that count was 0 for Artemis, but nothing enforced it. BUILD.md now makes it a check.

Measured tonight: on 208K tokens of Artemis's own replies, the inputs of the projections exceed the calibrated scales in 100 of 240 places. Nearly all are in the MLP, up to 12× in the down projections of layers 9–15, 27–29 and 56, so those activations clip in production. The served model still picks the same greedy token as a pass with the same weights and BF16 activations 97.9% of the time, over 590,774 positions.

The attention output projection's measured peaks sit at about 1% of its calibrated value. That points to a difference in calibration convention, to be resolved before any rescale. As the review notes, night 7's −16% KL for importance-weighted rounding was measured against a Q5 reference on production-generated text, not against BF16, and says nothing about task quality.

- **Plan:**
  - Calibrate Artemis's own scales on held-out Swedish, tool, code and English text.
  - Report clipping per layer, and KL against BF16 Artemis on held-out text.
  - Run the quality suite before any change reaches production.

## 10. Generated-code evaluation and upstream fixes

**Confirmed.** HumanEval ran each generated program with `python -I` as the benchmark's own user, root in the container. `-I` isolates Python's import path, not the program.

- **Change:** `geval.py` runs each program in a throwaway `systemd-run` unit:
  - a dynamic unprivileged user, no network, a private `/tmp` and a read-only system;
  - no `/root` or `/home` and no new privileges;
  - memory, task and time limits.

  Before any generated code runs, a probe in the same sandbox must report that it can't reach the network, can't write to `/opt/models` or `/root`, and can't list `/root`; otherwise the evaluation stops. `GEVAL_UNSAFE_EXEC=1` is the explicit opt-out.
- **Validation:** pending a run in the container, since an unprivileged LXC may not allow every sandbox property. The probe is what decides.
- **Upstream:** #466 (merged 7 Nov, a shared-prefix slot fix) and #533 (merged 8 Nov, tool order) postdate production's 5 Nov base. Each gets its own branch and the regression set: cache, tool calls, vision, long context.
